# 评审报告格式契约（铁律）

本文件是 `/code-review review` 输出报告的**唯一正式格式契约**。
`templates/review_report_template.md`、`prompts/review_with_persona_prompt.md`
和 `personas/*.skill.md` 的"输出要求"段必须与本文件完全对齐，不得另起一套字段名。

> 迁移来源：旧 `huawei_code_review/SKILL.md` 的"输出报告模板"与"铁律格式块"。
> 旧文件内部存在一处矛盾——铁律格式块定义要求"连贯段落 + `【修改示例】`"，
> 但其底部"输出示例"却用了 `【问题根因】`/`【落地解决方案】` 拆字段写法。
> 实际部署的 persona（`reviewer-张示例-z00000001.skill.md` 强制约束 #6）明确**禁止拆字段**、
> 要求连贯段落。本契约据此统一为"连贯段落 + `【修改示例】`"，
> 同时保留 benchmark 依赖的 `【{分身姓名}意见】` token。`【问题根因】`/`【落地解决方案】`/`【问题描述】`/`【修改建议】` 等
> 拆字段写法**废弃**，不得在新工程中使用。

---

## 1. 报告整体结构

```
═══════════════════════════════════════════════════════════════
                    代码检视报告
═══════════════════════════════════════════════════════════════
检视Commit: <commit_id>
评审分身: <persona 姓名/工号>
代码变更文件: <文件数 / 文件清单摘要>
═══════════════════════════════════════════════════════════════

（可选）通用基线违规区
（若加载了 references/cpp-baseline.md 且命中，输出此区；否则省略）

## 评审意见

### 1. <严重程度>：<问题概要>
（铁律格式块 ×N，每条以 --- 分隔）

### 2. <严重程度>：<问题概要>
（铁律格式块 ×N）

## 总结
```

当前为单 persona 单 commit。多 persona 联合评审的"多次命中统计"表与跨分身去重暂不纳入，
`【多次命中】` 字段在单 persona 场景省略。

---

## 2. 铁律格式块（每条评审意见，必须严格遵守，不可修改）

每条意见从 `【{分身姓名}意见】` 独占一行开始，到 `---` 分隔符结束。

### 2.1 有代码示例时

```
【{分身姓名}意见】
【评审来源】{分身姓名}|{规则编号}-{规则名称}
【位置】{文件名}:{行号起始}-{行号结束}

{分身视角的连贯描述。问题是什么、为啥是问题、怎么改，一口气讲完。
允许自然提及代码片段，但完整代码放【修改示例】。}

【修改示例】
```{语言}
{可直接复制的代码方案}
```
---
```

### 2.2 无代码时

```
【{分身姓名}意见】
【评审来源】{分身姓名}|{规则编号}-{规则名称}
【位置】{文件名}:{行号}

{分身视角的连贯描述。}
---
```

### 2.3 多 persona 命中时（暂不启用）

```
【{分身姓名}意见】
【评审来源】{分身姓名}|{规则编号}-{规则名称}
【位置】{文件名}:{行号}
【多次命中】{其他分身姓名，逗号分隔}

{描述}

【修改示例】
```{语言}
{代码}
```
---
```

## 3. 字段规约

| 字段 | 必填 | 格式 | 说明 |
|------|------|------|------|
| `【{分身姓名}意见】` | 是 | `【<姓名>意见】` | 每条意见首行，独占一行。`{分身姓名}` 与 persona 文件标题一致。benchmark 按此 token 统计命中数。 |
| `【评审来源】` | 是 | `{姓名}\|{规则编号}-{规则名称}` | 规则编号取 persona 的 S/P/B/A/C/D 编号（如 `S01`）。无匹配规则时填 `{姓名}\|通用`。 |
| `【位置】` | 是 | `{文件名}:{行号}` 或 `{文件名}:{起}-{止}` 或 `{文件名}:{行1},{行2}` | **文件名不含路径前缀**，只取 basename。多行用起-止或逗号。 |
| `【多次命中】` | 否 | `{其他姓名},{其他姓名}` | 仅多 persona 命中同一位置时出现。单 persona 省略。 |
| 描述段落 | 是 | 自然段落 | 紧接元信息后，空行分隔。**连贯一段**，不拆成 问题根因/解决方案 等独立字段。 |
| `【修改示例】` | 否 | 一行标记 + 紧接代码块 | 有可落地代码时必出现。代码块可带语言标记。无代码时整个字段省略。 |
| `---` | 是 | 独占一行 | 每条意见结束分隔符，必须有。 |

---

## 4. 严重程度分组

所有意见按严重程度分组放置于 `## 评审意见` 下。每组用
`### {N}. {严重程度}：{问题概要}` 作为分组标题，N 从 1 递增连续编号。

严重程度词表（**固定四档**，从以下选取）：

| 严重程度 | 含义 |
|----------|------|
| 高危 | 安全漏洞、数据丢失、未定义行为、崩溃风险 |
| 中危 | 明显 Bug、资源泄漏、逻辑错误 |
| 低危 | 代码质量、可维护性、一致性 |
| 优化建议 | 风格、可读性、可选改进 |

> persona 历史评论的 CodeHub `severity_cn`（致命/严重/一般/提示 之类）由
> `/code-review review` 的 prompt 映射到这四档分组，不在报告里直接出现 CodeHub 原始词。
> 分组标题用本表四档词为准。

## 5. 通用基线违规区（可选）

若加载了 `references/cpp-baseline.md` 且 commit diff 命中基线规则，在 `## 评审意见`
**之前**输出基线违规区。每条格式：

```
【通用基线违规】{规则编号} - {规则名称}
【规则来源】通用基线-{第X条}
【级别】要求|建议
【位置】{文件名}:{行号}
【问题描述】{客观描述缺陷}
【整改建议】{可直接复制的代码方案}
```

基线违规区与 persona 专属意见区**字段名不同**（基线区用 `【问题描述】`/`【整改建议】`，
persona 区用连贯段落 + `【修改示例】`），二者不得混用。未加载基线时整区省略。
