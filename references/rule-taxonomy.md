# 规则分类法（S/P/B/A/C/D）

personas 规则编号与 `【评审来源】` 字段中的规则编号都基于本分类法。

## 六大类

| 类别 | 前缀 | 编号范围 | 范畴 |
|------|------|----------|------|
| 规范要求 | S | S01–S20 | 代码规范、命名、格式、注释、`const auto&`、作用域 |
| 性能要求 | P | P01–P10 | 效率、资源、拷贝开销、move 语义、容器选择 |
| 业务逻辑 | B | B01–B10 | 功能正确性、边界处理、错误码、防御性编程、空值安全 |
| 架构设计 | A | A01–A10 | 设计模式、模块划分、依赖关系、接口设计、RAII、分页方案 |
| 并发安全 | C | C01–C10 | 线程安全、锁使用、生命周期、数据竞争 |
| 细节可读性 | D | D01–D10 | 可维护性、代码清晰度、日志规范、注释质量、魔鬼数字、重复代码 |

## 编号规则

- 按六大类顺序编号：S → P → B → A → C → D。
- 同一评审人的规则在该类内连续编号，不同评审人独立编号。
- 示例：`S01`、`S02`、`P01`、`B01`、`A01`、`C01`、`D01`。
- 不是每个 reviewer 都必须凑齐六类——只为其历史评论确有体现的类别生成规则。

## 规则结构（persona 文件中每条规则）

```
### {编号} 【{类别名}】{规则名称}
**触发条件**：什么代码模式触发此规则
**检查方法**：如何识别问题（grep 关键词 / 代码特征）
**禁止模式**：具体不能怎么写——增强模式下直接引用 target_code 作反例
**推荐模式**：应该怎么写

【真实评论+代码样本】
- "{评论原文}"
  代码上下文（{文件名}:{行号}）：
  ```
  {context_lines，目标行用 >> 标记}
  ```

【提炼约束】{一句话核心要求}
```
