# C++ 公共基线评审规则

> 提炼自《华为 C++ 语言编程规范 V5.3》与《C++ 性能优化指南》(Optimized C++, Kurt Guntheroth)。
> `/code-review review` 时**可选加载**：若本文件存在且 commit diff 命中基线规则，
> 命中项输出到报告的"通用基线违规区"（格式见 `references/review-output-format.md` §5），
> 随后再由 persona 分身做专项审查。基线只覆盖通用低级问题，不替代 persona。

## 评审输出格式（基线违规区）

基线违规**不**使用本文件自带格式，统一遵循 `references/review-output-format.md` §5：

```
【通用基线违规】{规则编号} - {规则名称}
【规则来源】通用基线-{第X条}
【级别】要求|建议
【位置】{文件名}:{行号}
【问题描述】{客观描述}
【整改建议】{可直接复制的代码方案}
```

注意：基线区字段名（`【通用基线违规】`/`【规则来源】`/`【级别】`/`【问题描述】`/`【整改建议】`）
与 persona 专属意见区（`【{分身姓名}意见】`/连贯段落/`【修改示例】`）不同，二者不得混用。

## 一、命名规范 (G.NAM)

### G.NAM.01-CPP 使用一致的命名风格
- **级别**: 要求
- **检查点**:
  - 类/结构体/枚举/typedef/类型别名: PascalCase (如 `HttpRequest`)
  - 变量/函数参数/类成员: camelCase (如 `sendRequest`)
  - 宏/常量/枚举值: UPPER_SNAKE_CASE (如 `MAX_SIZE`)
  - 私有成员变量建议加 `m_` 前缀或 `_` 后缀

### G.NAM.02-CPP 文件名与内容匹配
- **级别**: 要求
- **检查点**:
  - C++源文件使用 `.cpp` 扩展名
  - 头文件使用 `.h` 扩展名
  - 文件名应与文件中定义的主要类/函数名一致

## 二、格式规范 (G.FMT)

### G.FMT.01-CPP 使用统一的缩进
- **级别**: 要求
- **规则**: 使用4个空格缩进，禁止使用Tab字符

### G.FMT.03-CPP 行宽限制
- **级别**: 建议
- **规则**: 每行代码不超过120个字符

### G.FMT.05-CPP 变量声明每行一个
- **级别**: 要求
- **反例**: `int i, j, k;`
- **正例**: 每行只声明一个变量

### G.FMT.08-CPP 函数返回类型放在行首
- **级别**: 建议
- **正例**:
  ```cpp
  int Foo() {
      return 0;
  }
  ```

### G.FMT.12-CPP 控制语句必须使用大括号
- **级别**: 要求
- **反例**: `if (cond) return;`
- **正例**: `if (cond) { return; }`

## 三、函数规范 (P.FUN / G.FUN)

### P.01-CPP 合理选择函数参数与返回类型
- **原则**:
  - 小类型（≤2个指针大小）按值传递
  - 大类型使用 `const T&` 传递
  - 可移动类型考虑使用右值引用 `T&&`

### P.03-CPP 对所有外部数据进行合法性校验
- **级别**: 要求
- **检查点**:
  - 不信任任何外部输入（用户输入、网络数据、配置文件等）
  - 校验数据范围、长度、格式
  - 防御整数溢出

### G.FUN.01-CPP 函数功能要单一
- **级别**: 要求
- **检查点**:
  - 函数长度≤50行
  - 参数个数≤5个
  - 嵌套层级≤4层
  - 只做一件事，做好一件事

### G.FUN.03-CPP 禁止函数有未被使用的参数
- **级别**: 要求
- **处理**: 如果参数确实不需要，删除或使用 `[[maybe_unused]]`

### G.FUN.07-CPP 不要使用std::move返回函数局部变量
- **级别**: 要求
- **原因**: 会阻止RVO（返回值优化），导致性能下降

## 四、类与对象规范 (P.CLS / G.CLS)

### P.04-CPP 类的设计应该保证其封装性
- **原则**: 成员变量应该是private，通过public接口访问

### P.05-CPP 避免构造不完整的对象
- **原则**: 构造函数中应该完成所有必要的初始化

### P.06-CPP 明确需要实现哪些特殊成员函数
- **级别**: 建议（Rule of Three/Five/Zero）
- **规则**:
  - 如果需要自定义析构函数，通常也需要自定义拷贝构造函数和拷贝赋值运算符
  - 考虑使用 =default 或 =delete

### G.CLS.01-CPP 类的成员变量必须显式初始化
- **级别**: 要求
- **方式**: 声明时初始化或构造函数初始化列表

### G.CLS.02-CPP 成员变量优先使用声明时初始化或构造函数初始化列表
- **级别**: 建议
- **优先顺序**: 声明时初始化 > 构造函数初始化列表 > 构造函数体内赋值

### G.CLS.03-CPP 单参数构造函数声明为explicit
- **级别**: 要求
- **原因**: 防止隐式类型转换

### G.CLS.04/05-CPP 拷贝/移动构造函数和赋值运算符应同时声明
- **级别**: 建议
- **原则**: 成对声明，保持一致性

### G.CLS.06-CPP 禁止在构造函数和析构函数中调用虚函数
- **级别**: 要求
- **原因**: 此时虚函数不会调用到派生类的实现

### G.CLS.07-CPP 多态基类的拷贝/移动操作必须为非public或delete
- **级别**: 要求
- **原因**: 防止对象切片问题

### G.CLS.08-CPP delete、移动构造/赋值、swap函数应该有noexcept声明
- **级别**: 建议
- **原因**: 保证异常安全

### G.CLS.09-CPP 移动操作必须将源对象的资源正确重置
- **级别**: 要求
- **原则**: 移后源对象应处于有效但未指定状态

### G.CLS.10-CPP 通过基类指针释放派生类时，基类析构函数必须为虚函数
- **级别**: 要求
- **原则**: 避免内存泄漏

### G.CLS.11-CPP 在派生类中重写虚函数时禁止重新定义缺省参数值
- **级别**: 要求
- **原因**: 虚函数动态绑定，缺省参数静态绑定，会导致混乱

### G.CLS.12-CPP 在重写虚函数时应明确指定override或final
- **级别**: 要求
- **原因**: 编译器检查，防止拼写错误

### G.CLS.13-CPP 禁止重新定义public继承而来的非虚函数
- **级别**: 要求
- **原因**: 会造成隐藏和意外行为

### G.CLS.15-CPP 禁止重载逗号操作符、&&操作符和||操作符
- **级别**: 要求
- **原因**: 会改变求值顺序语义，导致意外行为

## 五、常量与类型 (P.CNS / G.CNS)

### P.07-CPP 尽量使用const语义
- **原则**: 能const的地方就const，包括变量、参数、成员函数

### G.CNS.01-CPP 禁止使用小写字母"l"作为数值型字面量后缀
- **级别**: 要求
- **原因**: 容易与数字1混淆

### G.CNS.03-CPP 对于不会修改成员变量的成员函数应使用const修饰
- **级别**: 要求

### G.CNS.04-CPP 对于指针和引用类型的参数，如果不需修改应使用const修饰
- **级别**: 建议

---

## 六、枚举规范 (P.ENU / G.ENU)

### P.08-CPP 避免将表达式转换为枚举类型
- **原则**: 枚举不是整数的别名

### G.ENU.01-CPP 优先使用枚举类而不是普通枚举
- **级别**: 建议
- **原因**: 枚举类有作用域，不会隐式转换为int

### G.ENU.02-CPP 避免定义未命名的枚举
- **级别**: 建议
- **原则**: 无名枚举只应用于声明编译期常量

---

## 七、表达式与语句 (P.EXP / G.EXP)

### P.09-CPP 保持作用域尽量小
- **原则**: 变量在使用处附近声明，不要提前声明

### P.10-CPP 合理使用auto
- **原则**: 避免类型冗长，但要保证代码可读性

### G.EXP.03-CPP 使用using定义类型别名
- **级别**: 建议
- **原则**: 优先使用 `using` 而非 `typedef`，更清晰易读

### G.EXP.05-CPP 禁止通过声明的方式引用外部函数接口和变量
- **级别**: 要求
- **原则**: 使用 `#include` 而非 `extern` 声明

### G.EXP.06-CPP 避免使用全局变量
- **级别**: 建议
- **原则**: 全局变量是维护地狱，考虑使用单例或依赖注入

### G.EXP.07-CPP 禁止依赖不同编译单元内全局对象的初始化顺序
- **级别**: 要求
- **原因**: 全局对象初始化顺序未定义

### G.EXP.08-CPP 确保对象在使用之前已被初始化
- **级别**: 要求
- **原则**: 声明时初始化，不要依赖默认值

### G.EXP.09-CPP 变量被使用时才声明并初始化
- **级别**: 建议
- **原则**: 缩小变量作用域

### G.EXP.10-CPP 不要在嵌套作用域中重用名称
- **级别**: 建议
- **原因**: 容易导致混淆

### G.EXP.11-CPP 优先使用{}初始化语法
- **级别**: 建议
- **原因**: 统一语法，防止窄化转换

### G.EXP.14-CPP 使用由C++提供的类型转换操作
- **级别**: 要求
- **规则**:
  - `static_cast` - 编译时类型转换
  - `dynamic_cast` - 安全的向下转型
  - `reinterpret_cast` - 底层类型重解释（尽量避免）
  - `const_cast` - 移除const（尽量避免）

### G.EXP.15-CPP 避免使用reinterpret_cast
- **级别**: 建议
- **原因**: 类型安全的大敌

### G.EXP.17-CPP 避免隐式有损算术转换
- **级别**: 要求
- **原则**: 大类型赋值给小类型时要显式转换并检查

### G.EXP.18-CPP 避免整数与指针间的互相转换
- **级别**: 要求
- **原因**: 64位系统上指针和整数大小可能不同

### G.EXP.19-CPP 禁止使用std::move操作const对象
- **级别**: 要求
- **原因**: const对象无法移动，会退化为拷贝

### G.EXP.20-CPP 确保有符号整数运算不溢出
- **级别**: 要求
- **原则**: 有符号整数溢出是未定义行为

### G.EXP.21-CPP 确保无符号整数运算不回绕
- **级别**: 要求
- **原则**: 无符号溢出会回绕，可能导致安全问题

### G.EXP.22-CPP 确保除法和余数运算不会导致除零错误
- **级别**: 要求
- **检查**: 除数必须非零

### G.EXP.23-CPP 只能对无符号整数进行位运算
- **级别**: 要求
- **原因**: 有符号整数的位运算结果未定义

### G.EXP.25-CPP 表达式中不要混用有符号数和无符号数
- **级别**: 要求
- **原因**: 会导致意外转换和溢出

### G.EXP.27-CPP 使用恰当的基本类型作为操作符的操作数
- **级别**: 要求

### G.EXP.28-CPP bool类型比较应避免多余的==或!=
- **级别**: 建议
- **正例**: `if (flag)` 而非 `if (flag == true)`

### G.EXP.30-CPP 用括号明确表达式的操作顺序
- **级别**: 建议
- **原则**: 不要过分依赖默认优先级

### G.EXP.31-CPP 不要依赖未计算的操作数中的副作用
- **级别**: 要求
- **原则**: 条件表达式中可能有操作数不被求值

### G.EXP.32-CPP &&和||操作符的右侧操作数不要包含副作用
- **级别**: 要求
- **原则**: 短路求值可能导致副作用不发生

### G.EXP.34-CPP 编译期可确定的断言检查使用static_assert
- **级别**: 建议
- **原则**: 编译期错误比运行期错误更好

### G.EXP.35-CPP 使用nullptr作为空指针常量
- **级别**: 要求
- **原则**: 不要用NULL或0

### G.EXP.36-CPP 控制表达式的结果应是布尔值
- **级别**: 要求
- **原则**: 不要用整数或指针隐式转换为bool

### G.EXP.37-CPP switch语句要有default分支
- **级别**: 要求
- **原则**: 处理所有可能情况，即使认为已穷尽

### G.EXP.40-CPP 禁止使用浮点数作为循环计数器
- **级别**: 要求
- **原因**: 浮点数精度问题可能导致循环次数错误

### G.EXP.41-CPP 避免在基本for循环的循环体中修改循环控制变量
- **级别**: 建议
- **原则**: 在迭代表达式中修改控制变量

### G.EXP.42-CPP 避免使用goto语句
- **级别**: 建议
- **原则**: goto破坏程序结构，仅在不使用会造成更复杂代码时使用

## 八、资源管理 (P.RES / G.RES)

### G.RES.01-CPP 外部数据作为数组索引或内存操作长度时需校验合法性
- **级别**: 要求
- **检查点**:
  - 校验索引在有效范围内（注意差一错误）
  - 校验长度不超过缓冲区大小
  - 外部数据必须严格校验

### G.RES.02-CPP 不能使用未初始化的内存
- **级别**: 要求

### G.RES.03-CPP 避免访问已释放的内存
- **级别**: 要求
- **原则**: 释放后置空指针，使用智能指针

### G.RES.04-CPP 不要访问超出生命周期的对象
- **级别**: 要求
- **原则**: 注意局部变量地址不要返回或传递到外部

### G.RES.06-CPP 禁止解引用可能为空的指针
- **级别**: 要求
- **原则**: 使用前先判空

### G.RES.14-CPP 避免出现delete this操作
- **级别**: 建议
- **原则**: 除非在资源管理器/生命周期管理器等特殊场景

## 九、错误处理 (P.ERR)

### P.13-CPP 使用恰当的错误处理机制
- **原则**:
  - 优先使用异常处理错误
  - 兼容旧接口时使用原有错误处理方式
  - 异常不安全代码使用其他方式

### P.14-CPP 异常仅用于处理错误
- **原则**: 不要用异常做正常控制流

### P.15-CPP 要提供基本的异常安全保证
- **原则**:
  - 基本保证: 不泄露资源，数据结构不处于非法状态
  - 强保证: 异常发生时无副作用

### P.16-CPP 不要盲目catch，不能处理的异常要继续传播
- **原则**: 不要吞掉异常，只捕获能处理的异常

## 十、并发安全 (P.CON / G.CON)

### P.17-CPP 使用合适的同步机制保护共享数据
- **原则**:
  - 多线程共享数据必须加锁
  - 优先使用std::lock_guard和std::unique_lock
  - 考虑使用std::atomic进行无锁编程

### P.18-CPP 多线程写同一内存位置需要同步
- **级别**: 要求
- **原则**: 使用互斥锁或原子操作

### P.19-CPP 使用volatile访问特殊内存后不能假设即时可见
- **原则**: volatile不保证线程安全，只用于硬件寄存器访问

### P.20-CPP 不要使用std::atomic类型但使用非原子操作访问内存
- **级别**: 要求
- **原则**: 一致性访问

### P.21-CPP 尽量缩短在临界区内停留的时间
- **原则**: 临界区内不做耗时操作，最小化锁粒度

### P.22-CPP 多线程程序中要特别留意对象的生命周期
- **原则**: 明确每个对象的生命周期由哪个线程负责

### G.CON.01-CPP 使用条件变量的wait方法时必须外加条件判断，并在循环中等待
- **级别**: 要求
- **原因**: 应对虚假唤醒(spurious wakeup)
- **正例**:
  ```cpp
  while (!condition) {
      cv.wait(lock);
  }
  // 或使用带谓词的wait
  cv.wait(lock, [&]{ return condition; });
  ```

## 十一、头文件与包含 (G.INC)

### G.INC.01-CPP 头文件必须包含防重复包含机制
- **级别**: 要求
- **方式**: #pragma once 或 #ifndef/#define/#endif

### G.INC.11-CPP 使用命名空间来管理全局函数、全局常量和全局类型
- **级别**: 建议
- **原则**: 避免污染全局命名空间

### G.INC.12-CPP 对于cpp文件中不需要导出的变量、常量或函数，应使用匿名namespace封装
- **级别**: 建议
- **原则**: 限制内部链接，避免命名冲突

---

## 十二、标准库使用 (P.STD / G.STD)

### P.25-CPP 优先使用C++标准库
- **原则**:
  - 用特殊成员函数替代memset/memcpy/memcmp操作对象
  - 使用std::string替代C风格字符串
  - 使用std::vector/std::array替代原生数组
  - 使用C++文件流替代C文件操作
  - 使用C++多线程库替代POSIX thread

### G.STD.01-CPP 使用新的标准头文件
- **级别**: 要求
- **原则**: 使用 `<cstdlib>` 而非 `<stdlib.h>`

### G.STD.02-CPP 使用std::string表示字符串
- **级别**: 建议
- **原则**: C++17及以后使用std::string_view表示字符串常量

### G.STD.03-CPP 禁止从空指针创建std::string
- **级别**: 要求
- **原则**: 构造前检查nullptr

### G.STD.04-CPP 不要保存std::string类型的c_str和data成员函数返回的指针
- **级别**: 要求
- **原因**: 字符串修改后指针可能失效

### G.STD.16-CPP 禁止调用abort、exit、quick_exit等函数终止程序
- **级别**: 要求
- **原则**: 正常返回或使用异常，让资源正确释放

### G.STD.17-CPP 禁止调用kill、TerminateProcess函数直接终止其他进程
- **级别**: 要求
- **原则**: 先通知安全退出，超时后再强制终止

### G.STD.18-CPP 使用库函数时避免竞争条件
- **级别**: 要求
- **原则**: 注意不可重入函数（如strtok, getenv）在多线程中的问题

### G.STD.19-CPP 禁止在信号处理例程中调用非异步安全函数
- **级别**: 要求
- **原则**: 信号处理函数中只能调用异步信号安全函数

## 十三、未定义行为防范

### UND.01 不惜一切代价避免未定义行为
- **原则**: 未定义行为后果任意严重，从崩溃到安全漏洞
- **常见未定义行为**:
  - 访问未初始化变量
  - 解引用空指针或野指针
  - 数组越界访问
  - 有符号整数溢出
  - 除零
  - 多线程数据竞争

### UND.02 不要对未定义行为做任何假设
- **原则**: 不要假设某种有未定义行为的操作具有某种特定行为
- **反例**: 假设有符号整数溢出会绕回到负数

---

## 性能优化基线

### 一、算法优化 (PERF.ALG)

#### PERF.ALG.01 使用预计算替代运行时计算
- **原则**: 将运行时可以预先计算的值提取到编译期或初始化阶段
- **示例**: 查找表、常量表达式、constexpr函数

#### PERF.ALG.02 延迟计算（Lazy Evaluation）
- **原则**: 只在真正需要时才执行计算
- **应用**: 避免不必要的对象构造、条件计算

#### PERF.ALG.03 批量处理替代逐个处理
- **原则**: 将多个操作合并为批量操作，减少函数调用开销

#### PERF.ALG.04 缓存计算结果
- **原则**: 对于昂贵的计算，缓存结果避免重复计算
- **注意**: 权衡内存使用和计算开销

#### PERF.ALG.05 使用特化算法
- **原则**: 针对特定场景使用专门的算法实现
- **示例**: 对小数据使用线性查找而非二分查找

#### PERF.ALG.06 优化常见路径
- **原则**: 针对最常见的输入情况进行优化
- **示例**: if-else中将概率高的分支放在前面

#### PERF.ALG.07 使用散列（Hash）优化查找
- **原则**: 对于频繁查找的场景，使用unordered_map等散列容器
- **注意**: 设计好的散列函数，避免冲突

#### PERF.ALG.08 双重检查优化
- **原则**: 对于昂贵的条件检查，先用廉价检查过滤
- **示例**: 先检查标志位再检查详细条件

#### PERF.ALG.09 使用闭式解替代迭代
- **原则**: 数学计算中优先使用直接公式而非迭代求解
- **示例**: 等差数列求和用公式n*(a1+an)/2而非循环

#### PERF.ALG.10 选择合适的大O算法
- **原则**: 根据数据规模选择最优复杂度的算法
- **参考**: O(1) > O(log n) > O(n) > O(n log n) > O(n²)

#### PERF.ALG.11 避免斯特潘诺夫抽象惩罚
- **原则**: 标准库通用算法可能有性能开销，关键路径可手工优化
- **说明**: 标准库算法为了保证通用性，可能不如针对特定场景手工编码的算法

---

### 二、动态内存优化 (PERF.MEM)

#### PERF.MEM.01 优先使用unique_ptr而非shared_ptr
- **原则**: unique_ptr零开销，shared_ptr有引用计数成本
- **注意**: 除非确实需要共享所有权，否则不要用shared_ptr

#### PERF.MEM.02 使用"主指针"模式管理动态对象
- **原则**: 一个对象只有一个所有者，其他使用原始指针/引用

#### PERF.MEM.03 预分配容器容量
- **原则**: 使用reserve/preallocate避免多次重新分配
- **示例**: vector::reserve、string::reserve

#### PERF.MEM.04 循环外复用动态变量
- **原则**: 在循环外部创建动态对象，循环内复用
- **反例**: 在循环内部反复创建/销毁临时对象

#### PERF.MEM.05 使用内存池优化频繁分配
- **原则**: 对频繁创建销毁的小对象使用内存池

#### PERF.MEM.06 避免内存碎片
- **原则**: 尽量使用固定大小的分配，或使用连续存储容器

#### PERF.MEM.07 减少动态内存分配次数
- **原则**: 优先使用栈分配、静态分配，减少堆分配

---

### 三、循环优化 (PERF.LOOP)

#### PERF.LOOP.01 缓存循环终止条件
- **原则**: 将循环终止条件中不变的计算提取到循环外
- **反例**: `for (i = 0; i < strlen(s); i++)`
- **正例**: `for (i = 0, len = strlen(s); i < len; i++)`

#### PERF.LOOP.02 递减优于递增（某些处理器）
- **原则**: 递减到零的比较在某些处理器上更高效
- **示例**: `for (i = n; i > 0; --i)`

#### PERF.LOOP.03 移除循环不变代码
- **原则**: 将循环内不随迭代变化的计算移到循环外

#### PERF.LOOP.04 循环内联小函数
- **原则**: 关键路径上的循环内避免函数调用开销

#### PERF.LOOP.05 循环展开
- **原则**: 适度展开循环减少迭代开销
- **注意**: 现代编译器通常会自动展开，谨慎手动展开

#### PERF.LOOP.06 使用范围for循环
- **原则**: 对于容器遍历，优先使用`for (auto& item : container)`

#### PERF.LOOP.07 循环内避免动态内存分配
- **原则**: 不要在循环内部进行new/delete或动态容器扩容

---

### 四、表达式优化 (PERF.EXPR)

#### PERF.EXPR.01 利用常量折叠
- **原则**: 编译期常量运算让编译器在编译时计算
- **示例**: `const int size = 24 * 60 * 60;` // 编译时计算

#### PERF.EXPR.02 使用移位和加法替代乘除
- **原则**: 对于2的幂次，使用移位操作替代乘除
- **示例**: `x * 8` → `x << 3`; `x / 2` → `x >> 1`
- **注意**: 现代编译器通常会优化，但显式表达更清晰

#### PERF.EXPR.03 整数计算优于浮点计算
- **原则**: 在精度允许的情况下，优先使用整数运算
- **说明**: 浮点运算单元复杂，很多处理器上更慢

#### PERF.EXPR.04 避免混合有符号/无符号运算
- **原则**: 混合运算会导致类型转换开销和潜在错误

#### PERF.EXPR.05 谨慎处理a/b*c表达式
- **原则**: 整数除法会截断，顺序影响结果
- **反例**: `2/3*10 = 0`（先做除法截断为0）
- **正例**: `2*10/3 = 6`（先乘后除）

#### PERF.EXPR.06 使用内联函数替代宏
- **原则**: 宏缺乏类型检查，可能产生副作用

---

### 五、控制流优化 (PERF.CTRL)

#### PERF.CTRL.01 使用switch替代if-else链
- **原则**: 当条件较多且基于整数/枚举时，switch通常更高效
- **说明**: 编译器可能优化为跳转表

#### PERF.CTRL.02 优化条件判断顺序
- **原则**: 将最可能为真的条件放在前面，减少判断次数

---

### 六、容器优化 (PERF.CONT)

#### PERF.CONT.01 默认使用vector
- **原则**: vector是最高效的通用容器，优先使用
- **说明**: 连续存储，缓存友好，遍历快

#### PERF.CONT.02 大数据量优先使用unordered_map
- **原则**: O(1)查找优于map的O(log n)
- **注意**: 需要设计好的散列函数

#### PERF.CONT.03 有序数据使用vector+二分查找
- **原则**: 对静态查找表，vector+lower_bound可能比map更快

#### PERF.CONT.04 预分配容器容量
- **原则**: 提前调用reserve避免多次重新分配和拷贝

#### PERF.CONT.05 选择合适的容器
- **参考**:
  - 频繁随机访问: vector
  - 频繁头尾插入: deque
  - 有序键值对: map（数据变化频繁）/ vector+sort（静态数据）
  - 快速查找: unordered_map
  - 频繁插入删除: list/forward_list（仅必要时使用）

---

### 七、字符串优化 (PERF.STR)

#### PERF.STR.01 使用string_view(C++17)替代const string&
- **原则**: 字符串只读访问时，string_view零拷贝

#### PERF.STR.02 使用+=或append替代+连接字符串
- **原则**: +运算符会创建临时对象，+=直接追加

#### PERF.STR.03 预分配字符串容量
- **原则**: 已知大小时先reserve，避免多次重新分配

#### PERF.STR.04 避免频繁字符串转换
- **原则**: 统一使用string，减少C字符串与C++字符串互转

---

### 八、其他优化 (PERF.OTHER)

#### PERF.OTHER.01 使用const引用传递大对象
- **原则**: 避免不必要的拷贝，使用 `const T&` 或 `const auto&`

#### PERF.OTHER.02 使用移动语义
- **原则**:
  - 用 `std::move` 转移资源所有权
  - 用 `emplace_back` 替代 `push_back`
  - 返回局部变量时不要std::move（阻止RVO）

#### PERF.OTHER.03 使用现代C++特性
- **原则**:
  - 使用constexpr进行编译期计算
  - 使用auto简化类型声明
  - 使用range-based for遍历容器

#### PERF.OTHER.04 优化I/O操作
- **原则**:
  - 使用缓冲区，减少系统调用
  - 二进制格式优于文本格式
  - 批量读写优于逐字节读写
